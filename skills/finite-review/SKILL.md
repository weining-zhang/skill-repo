# 有限轮次代码 / 文档审查

## 目标

对代码、技术方案、设计文档、接口文档、变更说明等内容进行有限轮次审查，发现高置信度、可验证、会影响交付质量的问题，并给出是否可以进入人工最终决策、合并或发布的判断。

本 skill 不追求完美代码或完美文档。审查结论服务于交付决策，避免 AI review 无限发散。

## 适用范围

适用于：

- PR / MR 代码审查
- AI 生成代码审查
- 产品规格、需求规格、技术规格审查
- 重构方案、技术设计、接口文档审查
- 上线前变更审查
- Bug fix 方案复审
- 已完成修改后的回归审查

不适用于：

- 单纯代码风格美化
- 创意型文案润色
- 无上下文的泛泛建议
- 纯主观偏好的命名、抽象、目录结构争论
- 没有明确交付目标的开放式“再看看”

## 输入与上下文

审查前尽量确认：

- 被审查内容：代码 diff、完整文件、技术文档或方案文档
- 审查目标：例如上线前风险审查、规格清晰度审查、接口兼容性审查、安全审查、性能审查
- 变更背景：为什么改，影响哪些模块，是否涉及用户数据、权限、支付、配置、缓存、部署等高风险区域

可选上下文包括上一轮审查结果、已修复问题列表、测试结果、业务规则、线上约束、兼容性要求、性能目标、安全要求、不希望审查的范围。

如果缺少上下文，应明确说明不确定性。不得假装确定，也不得把无法验证的问题列为阻塞问题。

## 轮次识别

如果用户未明确说明轮次，按以下规则判断：

- 没有历史审查结果或修复说明时，默认第一轮审查。
- 出现“已修复”“复审”“回归看一下”“再 review 一下”且提供上一轮问题或修改内容时，按第二轮或后续复审处理。
- 只要求验证指定修复项时，仅检查指定修复项和本轮修改直接引入的 P0 / P1。

## 审查流程

### 第一轮：完整但有边界

检查当前变更是否正确，是否存在 P0 / P1 / P2 问题，是否有明确测试或文档缺口，是否可以进入下一阶段。

第一轮也只输出有证据、能定位、能说明影响、能给出可执行建议的问题。不得为了显得完整而制造建议。

### 第二轮：收敛复审

只检查：

- 第一轮问题是否修复
- 修复是否引入新的 P0 / P1
- 是否存在第一轮遗漏的高置信度 P0 / P1
- 是否仍有未处理的 P2 需要人工取舍

第二轮不得重新开放式审查风格、结构、命名和非阻塞优化。

### 第三轮及以后：回归确认

只检查：

- 指定修复项是否完成
- 是否引入新的 P0 / P1
- 是否满足停止条件

第三轮及以后不得提出新的 P2 / P3，除非它们由本轮修改直接引入且影响明确。

## 审查纪律

只输出满足以下条件的问题：

- 有明确证据
- 能指出具体位置
- 能说明影响
- 能给出可执行建议
- 置信度足够高

不要输出：

- 低置信度猜测
- 主观风格偏好
- 命名洁癖
- 无证据的泛化建议
- 与本次变更无关的历史遗留问题
- 无法从当前材料验证的问题

低置信度或依赖业务规则确认的问题只能放入“需人工确认”，不得作为阻塞问题。

如果没有发现问题，应直接说明“未发现高置信度阻塞问题”，不得强行找问题。

## 证据位置要求

问题必须能定位到具体位置：

- 代码：文件路径 + 行号、diff hunk、函数名或测试名
- 文档：章节标题、条款编号、段落或表格
- 配置 / 部署：配置项、环境、命令、资源名或变更项

无法定位到具体位置的问题，不得列为 P0 / P1。

## 优先级定义

### P0：严重阻塞

满足任一条件即为 P0：

- 会导致严重线上事故
- 会导致数据丢失、数据错乱、资金错误
- 会绕过权限、认证、鉴权或安全边界
- 会造成敏感信息泄露
- 会导致核心链路完全不可用
- 会引发大范围崩溃或服务不可用
- 会破坏数据库、缓存、队列、文件等关键状态

处理规则：必须修复，未修复前不得合并或发布，修复后必须复审。

### P1：高风险阻塞

满足任一条件即为 P1：

- 核心功能逻辑错误
- 明确异常未处理导致流程中断
- 重要边界条件缺失
- 明显兼容性破坏
- 数据状态不一致
- 会影响主要用户路径
- 配置错误导致功能不可用
- 关键测试缺失且风险明确

处理规则：默认阻塞交付，必须修复或由负责人明确接受风险，修复后需要验证。

### P2：中风险非默认阻塞

满足任一条件可判为 P2：

- 非核心路径边界问题
- 维护性风险
- 可观测性不足
- 错误提示不清晰
- 性能隐患但暂无明确事故证据
- 文档与实现存在局部不一致
- 测试覆盖不足但不影响核心路径判断
- 后续扩展可能遇到问题

处理规则：不默认阻塞，需要建议本次修复、后续 backlog、接受风险或人工确认。

### P3：低风险优化

包括命名优化、代码风格、小范围重构、表达更清晰、注释增强、非关键重复代码、更优雅的实现方式、文档措辞优化。

处理规则：默认不进入正式审查结果。只有用户明确要求优化建议时才输出；复审阶段不得新增 P3。

## 代码审查重点

优先检查：

- 功能正确性
- 边界条件
- 异常处理
- 数据一致性
- 并发和事务问题
- 权限控制
- 输入校验和输出安全
- 兼容性
- 明显性能退化
- 缓存一致性
- 资源释放
- 日志、监控和告警
- 配置风险
- 测试缺口
- 回滚风险

## 文档审查重点

优先检查：

- 是否与代码、事实或约束一致
- 是否存在误导性描述或自相矛盾
- 是否遗漏关键前置条件、失败场景、边界条件
- 是否遗漏兼容性、安全限制、回滚方案、验证方式
- 操作步骤是否可执行
- 决策条件是否明确
- 责任边界是否清楚
- 验收标准是否明确

## Spec 审查重点

审查产品规格、需求规格、技术规格时，优先检查规格是否清晰、可实现、可验证：

- 目标、范围、非目标是否明确
- 术语、角色、对象、状态定义是否清晰
- 前置条件、后置条件、成功条件是否明确
- 核心流程、异常流程、失败场景是否闭合
- 边界条件、默认行为、空值 / 缺省值处理是否明确
- 输入、输出、数据模型、字段含义、约束和单位是否明确
- 状态流转、幂等性、并发、重试、超时规则是否明确
- 权限、安全、隐私、审计要求是否明确
- 兼容性、迁移、回滚、灰度、降级要求是否明确
- 性能、容量、可用性、可观测性等非功能要求是否可衡量
- 验收标准、测试口径、上线验证方式是否可执行
- 是否存在“合理”“尽快”“较快”“适当”等无法验证的模糊表述

Spec 审查不要替产品或负责人做业务决策。对于无法从材料确认的业务规则，应放入“需人工确认”。

## 停止条件

满足以下条件时，必须建议停止 AI review：

- 没有未解决的 P0
- 没有未解决的 P1
- P2 已经被修复、接受、记录为后续事项或交由负责人确认
- 没有新增高置信度阻塞问题
- 本轮审查没有发现影响交付的新增风险
- 剩余问题均不影响本次交付目标

建议措辞：

```text
已满足停止条件。建议停止 AI review，进入人工最终决策 / 合并 / 发布流程。
```

## 输出格式

正式审查优先使用以下格式。没有内容的区块可以用一句“无”代替；复审专用区块仅在复审时输出。

### 1. 总体结论

- 是否阻塞交付：
- 当前最高风险等级：
- 是否建议继续 review：
- 是否满足停止条件：

### 2. 阻塞问题

| 优先级 | 问题 | 证据位置 | 影响 | 建议修复 |
| ------ | ---- | -------- | ---- | -------- |

如果没有，写：

```text
未发现 P0 / P1 阻塞问题。
```

### 3. 非阻塞问题

| 优先级 | 问题 | 证据位置 | 影响 | 建议处理方式 |
| ------ | ---- | -------- | ---- | ------------ |

仅记录 P2。P3 默认不输出，除非用户明确要求优化建议。

### 4. 需人工确认

| 问题 | 不确定原因 | 需要确认的信息 |
| ---- | ---------- | -------------- |

只放无法从当前材料确认、但可能影响交付判断的问题。

### 5. 已修复项验证

仅复审时填写。

| 原问题 | 验证结果 | 说明 |
| ------ | -------- | ---- |

验证结果只能是：已修复、未修复、部分修复、无法确认。

### 6. 明确不处理项

| 问题 | 不处理原因 | 风险是否可接受 |
| ---- | ---------- | -------------- |

仅当用户或负责人明确选择不处理某项风险时填写。

### 7. 最终建议

只能选择一个：

- 可以进入人工最终决策 / 合并 / 发布
- 需要先修复 P0 / P1
- 需要负责人确认 P2 取舍
- 当前上下文不足，无法给出交付判断

## 推荐 Prompt

```text
请按“有限轮次代码/文档审查”进行审查。

审查目标：
只发现高置信度、可验证、会影响交付质量的问题，并判断是否可以进入人工最终决策 / 合并 / 发布。

轮次：
如果没有历史上下文，按第一轮审查。
如果是复审，只验证上一轮问题、修复引入的 P0/P1，以及是否满足停止条件。

禁止输出：
- 低置信度猜测
- 主观风格偏好
- 命名洁癖
- 无证据的泛化建议
- 与本次变更无关的历史问题

如果没有 P0/P1，请明确说明。
如果满足停止条件，请明确建议停止 AI review。
```

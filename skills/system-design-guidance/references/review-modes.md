# 系统设计指导与评审模式

根据用户目标选择一个主模式。多个对象同时存在时可以组合，但要分别给出阶段结论，避免把设计建议和已确认代码缺陷混在一起。

## 目录

- 模式选择
- 设计指导
- 方案 Review
- 实现 Review
- 事后反推
- 组合 Review

## 模式选择

| 用户目标或对象 | 主模式 | 核心结论 |
| --- | --- | --- |
| 新需求、重构、迁移、方案探索 | 设计指导 | 推荐模型、关键取舍、实现前决策 |
| 技术方案、设计文档、架构图、API 契约 | 方案 Review | 是否覆盖关键模型、能否实施 |
| 代码、diff、PR、已完成实现 | 实现 Review | 实际行为是否保持设计不变量 |
| 连续补丁、事故、回归、不稳定模块 | 事后反推 | 缺失模型和可复用条件模式 |

四种模式共享同一系统模型，但输入和比较对象不同：

```text
Requirements + Constraints
            |
            v
     [Design Guidance]
            |
            v
      Expected Model

Expected Model -----+
                    +--> [Proposal Review] --> Design Gaps
Proposal Model -----+

Expected Model -----+
                    +--> [Implementation Review] --> Findings
Actual Behavior ----+

Patches + Incidents --> [Retrospective] --> Missing Model --> Reusable Patterns
```

用户只说“帮我看看设计”时，根据当前主要证据判断：尚无方案则进入设计指导；已有方案则进入方案 Review；主要对象是代码则进入实现 Review。

## 设计指导

### 输入

- 需求目标、范围、非目标和验收条件。
- 现有系统边界、接口、状态、约束和已知问题。
- 不可改变的兼容、安全、性能、成本或发布时间条件。

### 动作

1. 建立预期系统模型和关键业务不变量。
2. 用六个风险面发现必须提前决定的问题。
3. 比较候选方案的正确性、复杂度、可恢复性和演进成本。
4. 推荐满足当前阶段的最小设计，不提前建设没有证据的通用框架。
5. 为每个关键决策定义验证方法和重新评估条件。

### 输出

1. 目标、范围、非目标和证据状态。
2. 推荐系统模型、边界、事实源、owner 和关键流程。
3. 候选方案与关键取舍。
4. 编码前必须锁定、可带约束延期、需要外部确认。
5. 核心不变量和验证矩阵。
6. 是否足以进入实现。

设计建议不是 finding。没有证据证明现有行为错误时，不使用 P0/P1/P2。

## 方案 Review

### 输入

- 被评审方案及其版本。
- 对应需求、现有系统事实、外部契约和约束。
- 明确的评审目标和不评审范围。

### 动作

1. 还原方案声明的系统模型和关键决策。
2. 检查目标、边界、状态、流程、副作用和验证是否相互一致。
3. 检查六个风险面中与需求相关的部分是否被覆盖。
4. 识别缺失决策、内部矛盾、不可验证约束和无依据复杂度。
5. 区分必须修改、可带条件接受和需要 owner 确认。

### Finding 要求

每条方案问题包含：

```text
位置：章节、图、接口或缺失决策
问题：
触发条件：
影响：
违反或缺失的不变量：
建议修改：
验收方式：
状态：必须修改 / 可带条件接受 / 需要外部确认
```

### 结论

只能选择一个：

- 方案足以进入实现。
- 方案可带明确条件进入实现。
- 方案需要先解决阻塞缺口。
- 当前事实不足，无法判断方案可实施性。

## 实现 Review

### 输入

- 代码、diff、PR 或 commit range。
- 需求、方案、API 契约和已接受设计决策。
- 相关测试、运行结果、日志和已知问题。

没有正式方案时，先从需求、现有代码和外部行为推断最小预期模型，并明确标注推断边界。

### 动作

1. 确认 change range、入口、调用方和最终副作用。
2. 把变更映射到受影响的风险面、流程线和不变量。
3. 沿真实读取、写入、异步、错误和 fallback 路径检查实际行为。
4. 检查代码是否引入方案未声明的新事实源、状态、owner、作用域、后台任务或生命周期。
5. 检查测试是否覆盖公开入口和最终效果，而不只覆盖被调用函数。
6. 只输出高置信度、有位置、有触发条件、有影响的问题。

### Finding 格式

```text
[P0/P1/P2] 标题
证据：文件、行号、调用路径或测试
触发条件：
实际行为与影响：
违反的设计决策或不变量：
建议修复：
回归验证：
```

优先级：

- P0：安全、资金、严重数据破坏或核心系统大范围不可用。
- P1：主要流程错误、状态不一致、关键边界失效或明确兼容破坏，默认阻塞。
- P2：非核心边界、可观测、恢复、性能或维护风险，不默认阻塞但需要取舍。
- P3：风格和优化建议，默认不输出。

Finding 必须由代码或运行证据支持。方案未写清但代码选择合理时，记录为设计追踪缺口，不直接判为代码缺陷。

### 输出

1. Findings，按严重度排序并放在最前。
2. 需要外部确认的设计语义。
3. 未覆盖的验证和剩余风险。
4. 简短实现与设计一致性结论。
5. 是否满足停止条件。

没有问题时明确写“未发现高置信度系统设计完整性问题”，并说明未执行或无法覆盖的验证。

## 事后反推

读取 [case-extraction.md](case-extraction.md)，从 commit、issue、事故、回归和当前实现中重建：

- 补丁频发信号。
- 反复跨越的未命名边界。
- 最初缺失的系统模型、决策和验证。
- 可用于后续设计指导的条件模式。

不得把当前项目参数直接晋升为通用规则。

## 组合 Review

当用户同时提供方案和代码时：

1. 先做方案 Review，确认预期模型和仍未决定的语义。
2. 再做实现 Review，比较代码实际行为。
3. 分开记录“方案本身缺失”和“代码偏离方案”。
4. 方案未定义的行为不能自动归责为实现错误；先判断它是否构成独立系统风险。
5. 输出一个总交付结论，但保留两类问题的证据来源。

实际需要有限轮次复审、P 级裁决和停止判断时，与 `finite-review` 组合使用，不在本 Skill 中复制完整 review 治理流程。

# 从流程线到决策点

使用本参考把风险面落到真实系统行为。不要围绕模块目录写抽象说明，要从业务触发追到最终副作用。

## 目录

- 还原流程线
- 选择流程线
- 识别决策点
- 决策卡
- 验证矩阵
- 输出收敛

## 还原流程线

按场景裁剪以下阶段：

```text
触发意图
  -> 准入条件 / readiness
  -> 冻结身份与执行快照
  -> 准备资源
  -> 执行工作
  -> 校验提交资格
  -> 最终副作用
  -> 对外暴露与观测
  -> 恢复、撤销或资源退出
```

每条线记录：

| 项目 | 要回答的问题 |
| --- | --- |
| 入口 | 谁在什么条件下触发？是否有多个入口？ |
| 输入事实 | 数据来自哪里？是权威事实、缓存还是快照？ |
| Owner | 谁拥有任务、状态、资源和最终提交权？ |
| 作用域 | 属于请求、任务、账号、租户、环境、进程还是全局？ |
| 状态变化 | 哪些状态被创建、冻结、更新、暴露、恢复或删除？ |
| 异步边界 | 哪些 `await`、回调、队列、定时器或远端操作可能乱序？ |
| 最终副作用 | 最终改变了哪个请求、文件、数据库、进程或用户结果？ |
| 失败路径 | 超时、取消、部分失败、重试和重启分别发生什么？ |

## 选择流程线

先覆盖主成功线，再依据风险选择补充线：

- 首次创建或首次使用。
- 正常读取和执行。
- 更新、替换、切换或迁移。
- 重复触发、并发和乱序完成。
- 超时、取消、失败、重试和恢复。
- 删除、撤销、退出和资源回收。
- 启动、重启、账号切换或环境变化。

不要为了完整而画所有流程。只有可能改变风险判断或实现边界的线才进入输出。

## 识别决策点

以下位置通常需要显式决策：

- 权威事实转成派生状态的位置。
- 状态跨作用域、进程、服务或团队边界的位置。
- 读取旧快照后跨异步边界再写回的位置。
- 多个入口可能操作同一状态或资源的位置。
- 主通道切换到 fallback 的位置。
- 调用返回“已受理”但工作尚未完成的位置。
- 删除、覆盖、迁移、计费、授权或外部请求发生之前。
- 失败、取消、超时、重启后决定是否继续的位置。
- 指标把内部状态映射成业务成功或失败的位置。

## 决策卡

设计指导和方案 Review 中，每个高风险决策点使用以下结构：

```text
Decision ID:
风险面：
流程线与位置：
已确认事实：
设计假设 / 待确认：
必须决定：
候选语义与取舍：
结论：
适用前提与例外：
必须成立的不变量：
最终校验位置：
状态：必须锁定或修改 / 可带约束延期 / 需要外部确认
验证方法：
```

技术手段必须服从语义。只有在写清重复、顺序、所有权、提交和失败语义后，才选择锁、队列、CAS、singleflight、generation、事务或不可变制品等实现。

实现 Review 中，把决策卡转换为 finding：增加文件、行号、调用路径、触发条件和实际影响，明确代码违反了哪个设计决策或不变量。无法定位到代码或运行证据的问题只能列为需要确认。

## 验证矩阵

验证项必须反向关联决策和不变量：

| Decision ID | 不变量 | 正常 | 边界 / 空值 | 并发 / 乱序 | 失败 / 恢复 | 兼容 / 发布 | 最终观测 |
| --- | --- | --- | --- | --- | --- | --- | --- |

验证优先级：

1. 从公开入口覆盖真实调用链。
2. 断言最终网络、文件、数据库、进程或用户可见副作用。
3. 覆盖会改变 owner、身份、revision 或作用域的时序。
4. 证明失败不会破坏上一份安全可用状态或无关资源。
5. 证明日志、事件或状态查询能够解释结果。

## 输出收敛

只输出会改变方案、实现或交付判断的决策与 findings。纯命名、代码风格和没有明确影响的抽象偏好不进入系统设计结论。

按当前模式收敛：设计指导在决策足以指导实现时停止；方案 Review 在阻塞缺口已解决或有明确 owner 时停止；实现 Review 在无未处理 P0/P1、P2 已取舍且关键验证明确时停止。

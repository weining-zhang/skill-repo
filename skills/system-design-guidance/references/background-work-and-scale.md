# 后台工作、关键路径与规模

当需求包含下载、解压、索引、缓存构建、预热、同步、安装、批处理、轮询或其它后台重任务时读取。

## 先定义优化目标

区分：

- 首次可交互时间。
- 首次用户任务耗时。
- 核心能力可用时间。
- 全部后台资源就绪时间。
- 吞吐、资源峰值和总工作量。

延后任务可能改善前台体验，但不会自动减少总工作量。不要只看平均耗时；检查 P95/P99、低配设备、冷启动和首次任务。

## 分离触发意图与执行就绪

后台任务经常有两个独立到达的事实：

- **Trigger Intent**：业务已经要求执行。
- **Execution Readiness**：资源、配置、身份和宿主阶段允许执行。

只有两者都成立才进入运行。设计时明确：

- 意图早到时是拒绝、排队、合并还是持久化。
- readiness 永不到达时是否超时、降级或放弃。
- 重复意图属于同一批次还是新一代任务。
- 身份或环境变化后，旧意图和旧 readiness 是否仍有效。

## 区分受理与完成

长任务 API 的成功可能只代表请求被受理。根据实际需要区分：

```text
accepted | queued | running | no-op | completed | failed | rejected
```

调用方必须知道返回的是哪个阶段，以及如何查询或接收终态。`no-op` 只能表示条件已经满足，不能伪造完成。

## 后台准入策略

候选策略包括：

- 语义 readiness：由最了解前台关键路径的 owner 发出领域信号。
- 固定延迟：仅用于实验、过渡或缺少信号时的有限兜底。
- Idle 或负载门控：按用户活动、CPU、I/O、网络或事件循环压力准入。
- 最长等待：防止 readiness 或 idle 条件导致永久饥饿。

选择策略前先明确前台关键路径和后台完成时限。固定等待不能证明业务就绪。

## 资源协调

先定义资源和竞争关系，再选实现：

- 使用全局预算限制总体 CPU、I/O、网络、磁盘和子进程压力。
- 对相同或重叠资源定义串行、互斥、合并或版本隔离语义。
- 多资源操作需要一致的获取顺序或无死锁协议。
- 等待者取消不代表共享底层工作结束；底层工作真正结束前不能错误释放 owner。
- 监控、扫描和维护任务拥有独立预算，不能无意成为业务 prerequisite。

## 规模放大

评估单机行为乘以设备、租户、任务和重试后的结果：

- 启动或发布是否让客户端在同一时间请求。
- 轮询间隔、分页和无变化请求产生多少流量。
- 重试是否带有上限、退避和抖动。
- 缓存、批次、singleflight 或去重发生在哪个范围。
- Trace、日志和指标本身是否放大网络与存储成本。
- 共享资源统计是否重复计算物理成本。

缓存、分批、抖动、限流和 CDN 是候选手段，不是所有场景的固定答案。

## 观测指标

同时观察前台和后台：

- `intent_to_start_ms`：意图到真正开始的等待。
- `readiness_wait_ms`：等待业务条件的时间。
- `work_duration_ms`：实际工作时长。
- `time_to_interactive_ms`：首次可交互时间。
- `first_action_latency_ms`：首次用户任务耗时。
- `time_to_ready_ms`：后台能力最终可用时间。
- 合并、重复、取消、恢复、终态失败和饥饿次数。
- CPU、I/O、网络、磁盘、内存和事件循环长尾。

先定义指标对象、阶段、分母、终态、排除项和缺失样本。诊断 Trace 不自动等于业务 KPI；审计记录也不适用普通 best-effort 策略。

## 最小验证矩阵

| 场景 | 验证重点 |
| --- | --- |
| 无后台工作 | 不增加关键路径等待和资源消耗 |
| 正常后台工作 | 前台不等待，后台在约定时限内完成 |
| readiness 前触发 | 意图按契约保留或拒绝 |
| 重复触发 | 复用、合并、排队或覆盖符合语义 |
| 多类任务并发 | 全局预算和资源协调生效 |
| 身份或环境切换 | 旧任务不向新上下文提交 |
| 调用方超时 | 底层 owner、锁和后续触发仍正确 |
| 重启恢复 | 恢复、重放或放弃符合契约 |
| readiness 永不到达 | 不永久饥饿，兜底符合安全约束 |
| 大规模发布 | 请求、重试、资源和观测成本可控 |

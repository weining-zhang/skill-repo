# 系统设计指导与评审

## 目标

使用统一的系统模型支持方案形成、方案 review、代码 review 和事后复盘。识别会改变业务行为、状态完整性、边界契约、失败安全、性能规模或系统演进能力的关键问题，并把它们落到真实流程、明确决策、不变量和验证证据上。

核心路径：

```text
Requirement / Proposal / Code / Patch
                  |
                  v
        Select Mode and Depth
                  |
                  v
          Six Risk Surfaces
                  |
                  v
     Critical Flows and Side Effects
                  |
                  v
  Decision / Design Gap / Code Finding
                  |
                  v
       Invariant and Verification
```

不要输出脱离现有系统的架构作文。不要机械遍历所有风险面。只保留有证据、有影响、会改变方案或实现判断的内容。

## 工作模式

先识别模式，再选择 Light 或 Deep。模式和深度相互独立。

### 设计指导

用于新需求、重构、迁移或架构探索。帮助建立系统边界、状态模型、关键流程、候选方案和取舍，输出需要锁定的决策与最小可验证设计。

### 方案 Review

用于技术方案、设计文档、架构图、API 契约或实施计划。检查方案是否覆盖关键不变量、完整生命周期、失败路径、兼容迁移、性能规模和验证方式，给出可实施、带条件可实施或需要修改的结论。

### 实现 Review

用于代码、diff、PR 或已完成实现。沿真实调用链检查代码是否实现并保持系统设计约束，是否在实际边界引入新的事实源、状态、生命周期、写入者、上下文作用域或副作用。只输出有代码证据和明确影响的设计完整性问题，不做普通风格 review。

### 事后反推

用于连续补丁、事故、回归或长期不稳定模块。从实现和补丁中反推缺失模型，并把稳定经验用于后续设计指导。使用此模式时读取 [case-extraction.md](references/case-extraction.md)。

各模式的输入、评审动作、输出和判断状态见 [review-modes.md](references/review-modes.md)。

## 深度分级

出现任一高风险信号时使用 Deep：

- 涉及权限、安全、隐私、资金、计费或关键数据完整性。
- 涉及删除、覆盖、不可逆迁移或可能破坏现有可用状态的副作用。
- 错误会造成大范围不可用、跨租户污染或难以恢复的数据错误。

没有高风险信号时，以下复杂度信号命中两项及以上，使用 Deep：

- 跨模块、进程、服务、客户端、团队或平台。
- 存在持久化状态、缓存、索引、本地制品或共享资源。
- 存在异步、后台、长耗时、定时或轮询任务。
- 同一操作存在多个触发入口、并发写入、重试或乱序完成。
- 包含创建、更新、切换、删除、恢复、回收等完整生命周期。
- 需要兼容旧版本、旧数据、旧协议或多平台行为。
- 单机行为可能放大为容量、资源、请求或监控成本。

其余情况使用 Light。简单、无状态、单入口、易回滚的局部修改可以 Quick Exit，不强行做系统设计展开。

- 使用任一正式 review 模式或需要对应输出模板时，读取 [review-modes.md](references/review-modes.md)。
- 使用 Deep 或需要完整风险分类时，读取 [risk-surfaces.md](references/risk-surfaces.md)。

- 出现持久状态、同步对账、更新替换、删除、迁移、重启恢复、账号或环境切换时，读取 [state-and-change-patterns.md](references/state-and-change-patterns.md)。

## 六个一级风险面

1. **事实与状态**：事实源、派生状态、执行快照、所有权、就绪和一致性。
2. **时间与生命周期**：创建、切换、取消、超时、并发、乱序、恢复和回收。
3. **边界与上下文**：职责、外部契约、作用域、身份传播、fallback、安全和信任。
4. **副作用与失败安全**：最终写入权、删除覆盖、失败策略、原子提交和可恢复性。
5. **性能与规模**：前台关键路径、后台准入、资源竞争、容量预算和放大效应。
6. **演进与运行保障**：兼容、迁移、灰度、回滚、可观测、诊断和指标口径。

六个面是通用分析坐标，不是固定问卷。方案设计时用它们寻找遗漏；方案 review 时用它们检查覆盖；实现 review 时用它们定位代码对系统模型的偏离。

## 统一工作流

### 1. 建立 Review Packet

确认：

- 当前模式、对象、范围和不审查范围。
- 目标、非目标、用户可见成功条件和关键业务不变量。
- 需求、现有系统、已接受方案、代码版本或 change range。
- 已确认事实、设计推断、建议方案和待确认问题。

没有设计文档时可以从代码和行为反推当前模型，但必须标明这是推断，不能把它包装成已接受设计。

### 2. 建立预期模型与实际模型

按当前阶段提取或构建：

- 系统边界、参与者和外部依赖。
- 事实源、派生状态、持久状态和执行快照。
- 状态与资源的 owner、写入者、读取者和作用域。
- 关键生命周期、触发入口和失败恢复路径。
- 最终网络、数据库、文件、进程或用户可见副作用。
- 必须成立的不变量、兼容约束和运行目标。

设计指导模式形成预期模型；方案 review 检查方案模型；实现 review 比较预期模型与代码实际行为；事后反推重建遗漏模型。

### 3. 扫描风险面

只保留可能导致以下后果的风险：

- 业务结果、数据、权限或计费错误。
- 主链路不可用或被后台工作阻塞。
- 身份、租户、环境或执行上下文串扰。
- 重复、乱序或迟到任务覆盖新状态。
- 删除、覆盖、迁移或恢复造成不可逆损失。
- 请求、重试、资源或观测成本被规模放大。
- 新旧版本、协议或持久状态无法共存。

按影响、证据强度、不可逆性和影响范围排序。不因某个面存在就制造问题。

### 4. 追踪关键流程线

从真实入口追到最终用户结果或外部副作用，不停在中间函数、内存对象或“请求已接受”。按场景裁剪：

```text
触发意图 -> 准入 / 就绪 -> 身份与快照 -> 执行 -> 提交资格校验
         -> 最终副作用 -> 对外暴露 / 观测 -> 恢复 / 退出
```

方案 review 要证明流程闭合；实现 review 要沿代码实际调用、数据和错误传播路径验证，不只检查方案中点名的函数。

### 5. 形成阶段性结论

- **设计指导**：形成候选方案、取舍、必须决策、可延期项和外部确认项。
- **方案 Review**：形成方案缺口、影响、修改建议、验收条件和评审结论。
- **实现 Review**：形成有文件或行号证据的 findings、触发条件、实际影响、修复建议和回归验证。
- **事后反推**：形成补丁信号、缺失模型、通用条件模式和前向验证方法。

先写语义和不变量，再选择锁、队列、CAS、singleflight、事务、轮询、不可变制品等实现手段。

### 6. 验证最终效果

验证必须关联决策、不变量或 finding，并优先覆盖公开入口、真实调用链和最终副作用。根据风险选择正常、边界、并发、乱序、取消、失败、恢复、重启、兼容、迁移、规模和回滚场景。

代码中的中间对象或单元测试通过，不足以证明最终请求、持久状态、文件、进程或用户结果正确。

## 证据纪律

- 区分已确认事实、从代码推断的行为、设计建议和待确认问题。
- 方案 review 的阻塞问题必须能定位到章节、契约或缺失决策。
- 实现 review 的 P0/P1 必须有文件、行号或具体调用路径证据，并说明可触发影响。
- 不能从当前材料验证的风险放入“需要确认”，不得伪装成已确认 finding。
- 不把技术偏好、命名、目录审美或无明确影响的重构建议列为系统设计问题。

## 输出与停止

按 [review-modes.md](references/review-modes.md) 使用当前模式的输出格式。

Light 只输出最高风险的 1 至 3 个面及少量关键结论。没有系统级风险时 Quick Exit：说明依据，只保留最多 2 条局部约束和 2 至 4 个验证点。

Deep 也只展开相关风险面，不要求六面平均输出。满足当前模式停止条件时明确停止：

- 设计指导：关键决策、不变量和验证足以指导实现。
- 方案 Review：所有阻塞缺口已修改、接受或交给明确 owner。
- 实现 Review：无未处理 P0/P1，P2 已修复、接受或记录，且关键回归验证明确。
- 事后反推：缺失模型和可复用模式已经有证据，不再从单一案例继续泛化。

## 职责边界

- 聚焦系统设计和实现的设计完整性，不替代普通局部代码正确性、风格或可读性 review。
- 实际 code review 可与 `finite-review` 组合：本 Skill 提供系统模型、风险面和不变量，`finite-review` 提供 finding 严重度、轮次收敛和交付停止纪律。
- 不替代文档治理；只评审方案内容和技术模型，不判断文档体系结构。
- 不替代上下文账本；长链路讨论中的事实、假设和决策状态由账本维护。
- 不替负责人决定业务策略；证据不足时说明不同选择对系统设计的影响。
- 不因案例来源携带领域词汇；案例只用于验证通用模式。

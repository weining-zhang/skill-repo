# Context Ledger

## 目标

为长链路问题维护外部状态，让讨论、事实、决策和方案草稿可追踪、可修正、可恢复。

核心原则：

```text
聊天 = 探索过程
账本 = 状态存储
代码 / 配置 / 运行结果 = 事实来源
决策日志 = 取舍依据
```

不要把完整聊天记录当成最终知识库。不要过早把探索性结论包装成最终方案。

## 资源读取

默认只使用本文件即可开展讨论和状态维护。

当需要创建或更新账本文档、需要固定模板、或用户要求“沉淀成文档”时，读取 [ledger-templates.md](references/ledger-templates.md)。

## 默认账本

优先兼容项目已有文档结构。若没有约定，默认使用：

```text
docs/context-ledger/
  problem.md
  decision-log.md
  solution-draft.md
  checkpoint.md
```

职责：

- `problem.md`：记录背景、目标、约束、范围、已确认事实、假设、未确认问题。
- `decision-log.md`：记录关键取舍、替代方案、原因、影响和状态。
- `solution-draft.md`：维护当前方案草稿、依赖前提、风险、待确认项。
- `checkpoint.md`：阶段性收敛，记录已接受结论、暂定结论、废弃方案、矛盾和下一步。

如果用户只要求轻量维护，可以只使用前三个文件；当讨论超过多个子问题、即将 context 压缩、或进入阶段转换时，启用 `checkpoint.md`。

## 工作模式

先识别当前模式：

- 讨论模式：用户明确说“先讨论”“不要改动”“先评估”时，不写文件，只在回复中给出建议同步项。
- 启动账本：用户要求沉淀、维护、创建上下文账本，且没有现有账本时，创建默认账本。
- 滚动维护：已有账本时，先读取相关账本文档，再继续分析或更新。
- 最终生成：用户要求最终方案时，只基于账本文档生成；先列出冲突、缺口和仍未确认项。

## 执行流程

1. 读取上下文
   - 查找用户指定文档路径或默认账本路径。
   - 若已有账本，先读取相关文件。
   - 若涉及代码、配置或运行行为，不把聊天假设当事实；需要取证时读取源码、配置、日志或命令输出。

2. 拆分长链路
   - 列出主链路。
   - 拆出每个环节的子问题。
   - 标明哪些问题需要代码确认，哪些可以先作为方案假设。
   - 标明当前讨论只覆盖哪个范围。

3. 标记信息类型
   - `[代码事实]`：来自文件、diff、配置或源码位置。
   - `[运行事实]`：来自实际命令、测试、日志或页面验证。
   - `[用户确认]`：来自用户明确确认。
   - `[讨论假设]`：当前可用但尚未验证的假设。
   - `[待确认]`：影响方案但尚未确认的问题。

4. 记录决策
   - 只有发生真实取舍时才写入决策日志。
   - 决策状态使用 `Proposed`、`Tentative`、`Accepted`、`Superseded`、`Rejected`。
   - 每条决策必须包含背景、选项、结论、原因、影响、重新评估条件。

5. 更新方案草稿
   - 只更新本轮讨论影响到的章节。
   - 把依赖前提和待确认项保留在方案旁边。
   - 不把未确认内容写成确定结论。
   - 发现前后矛盾时，先标出矛盾和证据，不直接覆盖旧内容。

6. 做 checkpoint
   - 每 3-5 个重要子问题后、阶段切换前、context 可能压缩前、或用户要求时执行。
   - 明确列出已接受结论、暂定结论、已废弃方案、新问题、矛盾、下一步。

## 更新纪律

更新账本文档时：

- 保留人工确认过的事实、约束、风险接受和决策理由。
- 对变更写出简短原因，而不是静默改写。
- 对被替代的结论标记 `Superseded`，不要无痕删除。
- 对缺失证据的内容标记 `[讨论假设]` 或 `[待确认]`。
- 避免每轮重写全文；优先小范围补丁式更新。

## 职责边界

需要做：

- 维护长讨论中的事实、假设、决策、开放问题和当前方案。
- 让 context 压缩后仍能从账本恢复状态。
- 在最终输出前检查账本冲突和缺口。
- 帮用户把探索过程逐步收敛成可追踪方案。

不需要做：

- 不替代代码 review；需要审查时使用对应 review 流程。
- 不替代 Change Report；代码改动稳定后的事实记录应交给变更记录流程。
- 不替代 Verification Report；测试和验证结论必须来自实际验证证据。
- 不把讨论过程中的临时假设包装成最终架构决策。

## 禁止行为

禁止：

- 根据压缩后的聊天记忆直接生成最终方案。
- 把暂定结论写成确定结论。
- 用新假设无痕覆盖旧决策。
- 在没有证据时声称“已确认”“已验证”“没有风险”。
- 机械维护过多文档，导致账本变成负担。
- 发现矛盾时自行脑补统一口径。

## 默认回复

讨论模式下，回复末尾可给出：

```text
本轮建议同步到账本：
- problem.md：
- decision-log.md：
- solution-draft.md：
- checkpoint.md：
```

写文件模式下，说明已更新哪些账本文档、哪些结论仍是暂定、下一步应确认什么。
